## 背景

### dsh-tui 是什么

TypeScript 写的 dsh 插件，运行在 dsh 进程内，基于 pi-tui 渲染。它与本仓库的架构不同：

| | dsh-tui | 本仓库 |
| --- | --- | --- |
| 语言与渲染 | TypeScript + pi-tui | Rust + Ratatui |
| 与 dsh 的关系 | 进程内插件 | 进程外，通过桥接插件和 ACP 连接 |
| 布局 | 单栏，对话占满 | 多区块，有 Agent 侧栏 |

所以只借鉴交互设计，不借鉴渲染层。

### 建模工作树的两条路线

| 路线 | 入口 | 谁拥有流程 | 状态 |
| --- | --- | --- | --- |
| 独立入口 | `--modeling <仓库>` | Rust 管 Python 子进程，Python 拥有建模阶段和模型调用 | 已提交 |
| 领域会话 | `--domain-context <文件>` 加 F6 视图 | dsh 会话拥有对话；建模能力以 MCP 工具 `modeling_domain` 挂入，通用工具强制 `read-only` | 未提交 |

领域会话路线符合“优先复用 dsh”的方向。本计划以它为准。

2026-10-12 观察到的状态：该工作树已合并到 `4f8464d`，正处在一次未完成的合并中，`src/backend/acp.rs` 有冲突待解决。

## 迭代 1：扩展点与结构化工具状态

这一轮只做两件事，都是后续迭代的前提。

### 1.1 领域视图成为通用扩展点

- 问题：F6 建模视图是写死在 UI 里的特例。再接第二个领域就要再改一遍 UI。
- 做法：把“领域快照、只读视图、受控确认”定成一个接口，建模是第一个实现。
- 参考：dsh-tui 的 `src/extension/overlay-manager.ts` 把叠加视图做成了扩展机制。
- 边界：Core 拥有领域事实，UI 只读快照、提交类型化命令。这与 `ui-module-boundaries.md` 一致。
- 结果：领域会话路线跑通建模全流程后，删除独立入口 `--modeling`，不再维护两套。

迁移及删除验收见[独立入口迁移核对](dsh-modeling-entry-migration.md)，已满足原删除前提。

### 1.2 Core 为工具消息提供结构化状态

- 问题：`ConversationItem` 没有结构化的工具状态字段。UI 靠解析摘要文本里的状态词（`done`、`failed`）上色，`tui-experience-iteration-plan.md` 已把它列为已知限制。
- 做法：Core 在快照里给出工具的类型、状态、命令或目标、退出码、输出行数、diff 统计。
- 为什么先做：工具卡片（迭代 3）和耗时行（迭代 2）都依赖它。

验收：建模视图通过扩展接口注册并通过现有回归测试；UI 不再解析工具摘要文本来判断状态。

## 迭代 2：长任务能力

建模是多阶段、长时间的任务。这一轮解决“看不出进展”和“中途无法纠偏”。

### 2.1 滚动锚点（最先做）

- 现象（推断）：流式输出时往上翻看，正在读的内容会被不断顶走。
- 原因：滚动位置记录的是“距离底部多少行”，底部每多一行，视口就下移一行。
- 做法：用户离开底部后，锚点固定在某条消息的某一行；回到底部后恢复跟随。
- 先复现再改：在真实终端里确认现象存在。

### 2.2 活动指示

- 问题：模型等首字或思考时屏幕不动，分不清是在等还是挂了。
- 做法：运行期间提示符显示活动标记，并定时重绘它。空闲时仍然不绘制帧。
- 参考：dsh-tui 的提示符 `●` 淡入、呼吸、淡出，50 ms 一帧。
- 约束：状态必须同时有文字，不能只靠颜色或动画；`NO_COLOR` 和 mono 下要可读。

### 2.3 分阶段耗时

```text
Model wait 1.0s · Thinking 2.0s · Response 3.0s · Completed 14:32:12
```

- 四个阶段：等首字、思考、输出、工具。流式过程中实时更新，结束后固定。
- 位置：这一步的最末尾，排在这一步的工具之后。
- 数据：由 Core 根据事件时间计算并放入快照，UI 只显示。

### 2.4 todo 与计划面板

- 作用：一直显示“现在在哪一步”。
- 数据来源：dsh 的 ACP 不提供计划更新（见“dsh 能力调研”）。todo 列表由 `zf-tui-bridge` 插件从持久事件 `todo/write` 补发，整份替换。

### 2.5 steering

- 作用：运行中追加引导，不必等轮次结束。现在只能排队。
- 约束：`GatePending` 期间不能发起新的 root turn 或 steer，这条不变量必须保留。

### 2.6 plan 评审

- 建模的受控写入本来就需要人确认，与 plan 评审是同一种交互。
- 做法：复用现有的审批面板，不新建一套。

验收：用确定性的本地 ACP 提供方（参照 `tests/fixtures/conversation_stream_check.py`）覆盖滚动锚点、耗时行和 steering 的拒绝路径。

## 迭代 3：输入与阅读

### 3.1 工具卡片

```text
● Tool / bash / Run the coverage gate
$ pnpm run test:coverage
/workspace/project
… +4 lines (Ctrl+O to expand)
[exit 0]

● Tool / edit
src/view.ts
- old line
+ new line
└ +1 -1 · 1 file
```

- 三种渲染：终端（命令、目录、输出、退出码）、diff（增删行加统计）、通用。
- 三档显示：预览、展开、隐藏。折叠时显示“还有 N 行”。
- 建模工具的输出通常很长，隐藏档对它最有用。
- 遗留问题：对话区没有行级光标，单独展开某一张卡片需要先引入选择模型。本轮先做整体三档。

### 3.2 思考过程内嵌

- 现状：思考是与回答并列的独立消息，有自己的标题。
- 做法：作为助手回答下的暗色小节显示。行数更少，主次更清楚。

### 3.3 按块序号排列

- 现象（推断）：思考与正文各合并成一条。“思考、正文、再思考”会被压成两段，丢失先后关系。
- 做法：按服务端的块序号保留顺序；块结束和消息结束时用权威内容替换累积的片段。
- 已有的一半：思考的最终摘要会纠正片段，已有测试覆盖。

### 3.4 同一轮的多步连成一条

- 现象：一轮里说一句、调一次工具、再说一句，会出现多个助手标题。
- 做法：工具隐藏时，后续步骤不重复标题。与 3.1 的三档显示一起做。

### 3.5 输入补全与命令

- `@文件` 路径补全。
- `/compact`。
- 其他插件注册的斜杠命令。
- `@session` 会话引用（可选，价值待确认）。

### 3.6 会话选择器

- 顶部搜索框，按标题过滤。
- 在“当前工作区”和“所有工作区”之间切换。
- 不可恢复的会话直接标出原因。

### 3.7 行内提示

- 重试：`Retrying model request (1/2) in 500ms: provider rate limit`。
- 压缩：`… earlier context was compacted …`。
- 都是对话流里的一行，不弹面板。

验收：每种工具卡片、每档显示都有 `TestBackend` 渲染断言；中文、emoji、组合字符和窄屏沿用现有的对比测试方式。

## 迭代 4：布局与性能

### 4.1 常驻区瘦身

- 现状：顶部 4 到 6 行常驻，底部另有状态区、输入框和快捷键行。小终端里对话空间受挤压。
- 做法：把目录、分支、模型、token、上下文占用压成贴在输入框上方的一行。
- 约束：顶部的执行、活动、证据、静默、attention、来源、下一步动作必须保留。可以紧凑排版，不能全部藏进详情页。

### 4.2 输入提示随状态变化

- 空闲时显示输入提示；运行中显示“Enter 引导，Esc 取消”这类当前可用的操作。
- 依赖迭代 2 的 steering。

### 4.3 尾部增量排版

- 现状：一条正在变化的消息每次整条重排，UI 文档已说明“不保证逐字符增量排版”。
- 做法：只重排最后一个未闭合的段落或代码块，前面已定型的行复用。

### 4.4 快照复制（先测量）

- 现象（推断）：Core 每次发布生成一份完整快照，UI 每次绘制再复制一份，都包含全部消息。
- 做法：先测量长历史下每个片段的实际开销，再决定是否改。不测量不动手。

验收：沿用 `cargo test --lib conversation_reuses_layout -- --nocapture` 的方式，为增量排版增加“只重排尾部”的计数断言；耗时只作同机参考，不作时间断言。

## 贯穿各迭代的不变量

- Core 是执行事实的唯一所有者；UI 只读快照、提交类型化命令。
- 保留稳定的 thread、turn、item 身份和 generation；旧 generation 的事件不进入对话。
- Gate 只由绑定的当前 child turn 完成、失败、中断或断连释放。
- 不记录凭据、完整提示词和未脱敏的工具输出；工具卡片显示的输出沿用现有的大小限制。
- 不确定的外部结果明确显示为 unknown，不自动重试副作用。
- 新会话、插件、配置能力优先复用 dsh，不自建平行体系。

## dsh 能力调研（2026-10-13）

对象是本机安装的 dsh 0.2.0-rc.2 发布包。“ACP 只转发整条消息”和“插件能订阅事件”用真实 dsh 跑过一轮确认，其余只读了源码。

### ACP 只转发已提交的整条消息

- `dsh-acp` 只监听四种持久事件：`assistant/message`、`tool/call`、`tool/result`、`turn/end`。
- 它发出的更新只有六种：思考块、正文块、工具开始、工具结束、用量、配置变更。
- `agent_message_chunk` 是一条已提交消息里的一个完整内容块，不是逐字片段。
- 逐字帧是进程内事件 `agent/assistant-stream`，`dsh-acp` 没有使用它。
- 实测：一次真实回答在提交时一次到达；同一请求的“开始输出”比它早约 0.5 秒。

后果：只看 ACP 无法区分等首字、思考和输出；流式相关的优化在真实 dsh 下触发得比预想少。

### 插件通道可以补上缺口

`dsh-plugin` 夹在 dsh 的 ACP 服务和 TUI 之间，自己掌握帧的收发，既能答 `zf/*` 请求，也能主动推通知。实测它能订阅 `session/event` 和 `agent/assistant-stream`。

| 计划项 | dsh 里已有的事实 | 状态 |
| --- | --- | --- |
| 2.3 耗时的阶段划分 | `agent/assistant-stream` 帧的类型：开始、思考增量、正文增量 | 已接：插件推 `zf/session/event` 的 `stage`，只在阶段变化时推一次 |
| 2.4 todo 面板 | 持久事件 `todo/write`，载荷是整份列表 | 已接：插件推 `todos`，Core 进快照，对话区底部显示 |
| 逐字流式、3.3 块顺序 | 同一批流式帧，带 turn、step 和修订号 | 已接：预览加权威替换，块在角色切换处分段 |
| 2.5 steering | `agent.steer(message)` 在下一步边界生效；`followup` 排到下一轮 | 已接：插件 `zf/session/steer` 只在轮次进行中接受，投递由 `steer` 事件确认；界面入口是 `/steer` |
| 2.6 plan 评审 | `plan/mode` 事件；`exit_plan_mode` 经“用户提问”通道发起评审 | 已接：插件注册为提问应答者，复用请求面板 |
| 3.5 `/compact` 与插件命令 | `commands` 服务的 `list(agent)` 和 `execute(agent, line)` | 已接：清单和执行都走插件，自己发起轮次的命令被拒绝 |
| 3.7 重试提示 | 持久事件 `llm/retry`：第几次、上限、延迟、失败原因 | 已接：对话流里的一行提示，只带 dsh 的失败代码 |
| 3.7 压缩提示 | `compaction/start`、`end`、`summary`、`prune` | 已接：同一次压缩一行，显示结果 |

### 约束

- 新增的通知对旧版 TUI 无害：桥接忽略不认识的通知方法。
- 阶段事件不带模型输出，只是标签；todo 内容限 100 条、每条 512 字符，插件和桥接各限一次。
- `zf-tui` profile 直接链接本仓库的 `dsh-plugin`，改插件会影响所有使用这个 profile 的运行。
