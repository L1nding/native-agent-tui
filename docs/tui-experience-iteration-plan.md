# TUI 视觉与体验迭代计划

日期：2026-10-09，2026-10-10 更新。状态：四轮迭代的主体已实现并在 Windows Terminal 中做过固定场景截图核对；宽屏详情区（Inspector）和按单个工具组展开仍未实现，见文末“当前实现与已知限制”。

## 目标与依据

把现有 TUI 做成有清晰阅读层级的 Agent 工作台：对话是视觉中心，Agent 和工具执行进展便于扫读，待处理请求容易发现，常用操作容易找到。

本计划最初基于源码与设计文档审阅。实施过程中用 `scripts/preview_tui.ps1` 在 Windows Terminal 打开固定合成快照并截图核对（暗色、浅色、mono，80–150 列）；没有用真实模型会话做视觉验收。沿用英文默认界面，并验证中文、emoji 和组合字符。

当前已有搜索、命令面板、Agent 树、时间线、请求详情、工作流、Context 和历史面板；优先重组呈现与导航。

| 现状证据 | 体验问题 | 对应迭代 |
| --- | --- | --- |
| `src/ui/layout.rs::main_layout` 顶部占 4/6 行，底部另有状态区、3 行输入区和快捷键行 | 小终端中对话空间受挤压，常驻信息权重接近 | 1、3 |
| `src/ui/render.rs::draw` 多个区块使用完整边框，颜色直接写在渲染代码中 | 分区较机械，缺少统一的焦点和状态样式 | 1 |
| `src/ui/render.rs::message_rows` 用角色标题、文本换行和空行组成消息 | 长回答、代码和工具摘要缺少阅读层级 | 2 |
| `src/ui/render.rs::draw` 在宽度至少 100 列且存在 Agent 时显示固定 32 列侧栏 | 布局选择较粗，侧栏与正文比例无法适配更多尺寸 | 3 |
| 输入区把换行呈现为 `↵`，命令面板已有 `Ctrl+P` 入口 | 多行任务难检查，已有功能的入口可以更清楚 | 3、4 |

遵守 `native-agent-tui-ui.md` 和 `ui-module-boundaries.md`：Core 拥有执行事实，UI 只读取快照、维护本地展示状态并提交类型化命令。现有顶部执行/活动/证据/静默/attention/来源/下一步动作契约必须保留；可以紧凑排版，不能把必需信息全部藏进详情页。

## 视觉方向

采用克制的终端工作台风格：对话区减少完整框线，侧栏降低对比，输入与当前焦点使用明确的强调线；正常信息安静，用户需要行动时突出。

- 建立语义样式：正文、次要文字、分隔线、选中、焦点、运行、等待、成功、失败、未知。状态同时有文字，不能只靠颜色表达。
- 主强调色先用青蓝；运行、等待、失败的状态色与选中态分开。默认适配终端背景，提供可验证的浅色和低色彩表现。
- 圆角仅用于输入框和浮层等需要聚焦的区域；正文使用留白、缩进和细分隔。
- 状态图形使用可回退的普通字符，不强制安装 Nerd Font，不依赖 emoji 的显示宽度。
- 本轮不增加常驻装饰图案或自动弹出的欢迎浮层；空会话提供简洁说明和常用入口。

目标布局示意（文案仅为设计示例，不代表新增状态事实）：

```text
 native-agent   workspace / model                     Running
 activity · evidence · silence · attention · source · next action
 ────────────────────────────────────────────────────────────────
 Agents             Conversation
                    You
 > root  Running    Review the current implementation
   child Waiting
                    Assistant
                    Findings and explanation…

                    > Tool summary             Running
                      Expand details
 ────────────────────────────────────────────────────────────────
 [requires action 时：请求摘要与下一步操作]
 ╭ Task ────────────────────────────────────────────────────────╮
 │ > Write a task…                                              │
 ╰──────────────────────────────────────────────────────────────╯
 Enter Send   Ctrl+P Commands   Ctrl+F Search   F1 Help
```

示意图中的 Agent 区、工具摘要和请求条按已有数据出现；窄屏使用单栏。具体高度由迭代 1 的截图验证决定。

## 迭代 1：视觉基础与主屏层级（P0）

**当前状态：已实现。** 语义主题（暗色、浅色、terminal、`NO_COLOR`/mono）集中在 `ui/theme.rs`；头部状态行、对话标题、状态条、输入框和快捷键行按层级着色，快捷键行按宽度省略低优先级项。

**用户可见结果：** 打开应用即可看出变化，对话更突出，状态和操作入口更容易识别。

工作项：

1. 先用固定只读快照捕获空会话、运行中、等待审批、失败/未知四组现状画面；不启动真实模型任务。
2. 新增 `src/ui/theme.rs`，集中管理语义颜色、文字强调和边框样式。先覆盖主屏、Agent 列表、输入框和命令面板，再迁移其余面板。
3. 重排顶部信息：会话/工作区/模型形成摘要行，执行证据形成独立状态区域。路径和次要配置按可用宽度缩略，完整信息仍可查看；必需执行信息保留可见。
4. 减少对话区完整边框，统一消息留白、焦点提示、侧栏选中态和输入框样式。
5. 底部按当前模式优先显示少量常用动作，完整快捷键仍从 F1 查看；处理窄屏截断。

主要范围：`ui/theme`（新增）、`ui/render`、`ui/layout`、`ui/workflow_view`、`ui/commands`。

验收：80×24、120×32、160×48 下主内容不重叠，输入和关键操作可见；运行、审批、失败、未知在无色环境中也能区分；默认、浅色终端背景下文字可读；交付同场景前后对照截图。

## 迭代 2：对话与工具阅读体验（P0）

**当前状态：已实现，Markdown 为最小子集。** `ui/conversation.rs` 提供唯一的对话投影：按词换行（CJK 可在字间断行）、角色标题着色、用户消息引导条、标题/列表/引用/行内代码/粗体/代码围栏的样式。定界符保持可见，所有源字符都在屏幕上。渲染、翻页和搜索定位共用这份投影。工具摘要按 Core 写出的状态词着色；一个轮次超过 4 次调用时折叠为计数行，保留未完成/失败的调用和最新一次调用，`Ctrl+E` 全部展开或折叠，搜索命中所在的工具组自动展开。表格、嵌套列表、链接和语法高亮没有专门处理，按纯文本显示。

**用户可见结果：** 长回答更容易阅读，工具过程可以快速扫过，搜索仍能准确跳到原内容。

工作项：

1. 为用户消息、助手消息和工具摘要定义不同的排版，明确“谁说的”和“这是内容还是执行信息”。
2. 支持最小 Markdown 展示：标题、列表、引用、行内代码、代码围栏；复杂表格与未闭合流式片段先采用可读的纯文本回退。语法高亮后置。
3. 工具摘要默认紧凑，按完整稳定标识展开当前快照可提供的详情。缺失内容显示 unavailable，不拼接日志猜测结果。
4. 保留回看位置和已有回到底部入口，使新消息提示更明确；流式输出不强行抢走用户的阅读位置。
5. 共用一套消息排版结果来计算渲染、滚动和搜索定位。正文样式化后仍保留源文本范围到显示行的映射。

主要范围：建议新增 `ui/conversation.rs` 负责消息投影、排版和位置映射；连接 `ui/render`、`ui/search`、`ui/tool_detail`。全局路由仍由根模块处理。

验收：中文/emoji/组合字符、长代码行、未闭合代码围栏、内容截断均可读；终端缩放、折叠和流式追加后搜索定位准确；草稿不受影响；不向 UI 引入新的执行状态推断。

依赖：迭代 1 的语义样式。风险重点是搜索和滚动映射，先完成位置映射再接入富文本。

## 迭代 3：自适应工作台与任务输入（P1）

**当前状态：已实现，详情栏只覆盖请求。** 已有共享工作区几何（`layout::workspace_layout` 返回侧栏、对话、详情栏三列，渲染和搜索定位共用）、1–5 行多行输入、秘密输入遮蔽、请求状态条，请求详情面板按真实输入区高度让位。至少 140 列且有待处理请求时显示请求详情栏。侧栏仍是 100 列一个断点。

**用户可见结果：** 多 Agent 时便于切换和对照，普通单会话不会被辅助面板挤占，多行任务可以直接检查。

工作项：

1. 在 `ui/layout` 中统一主屏几何计算，渲染和搜索跳转共用布局结果，消除各处对侧栏宽度的重复推算。
2. 初始断点方案：小于 100 列显示单栏；100–139 列允许 Agent 侧栏；至少 140 列允许按需打开详情区。侧栏宽度随可用空间有界调整，最终阈值由截图验证。
3. Agent 列表突出名称、父子关系、执行状态和待处理数量；展示字段只来自快照，不引入没有证据的百分比进度。
4. 输入框按内容从 1 行增长到最多 5 行，超出后内部滚动；短终端自动压缩。保留 Enter 发送及当前编辑约定，不在这轮静默更换键位。
5. 审批/用户输入采用显眼且稳定的请求条与详情入口；状态改变不吞掉正在编辑的内容，不自动提交回答。

主要范围：`ui/layout`、`ui/render`、`ui/workflow_view`、`ui/editor`、`ui/requests`、`ui/request_state`；根模块仅连接布局和焦点路由。

验收：跨越断点缩放时选中项、滚动位置和草稿保留；长路径、长 Agent 名称不挤坏布局；24×8、80×16 等极小尺寸可操作或明确提示调整窗口；完整 `RequestRef` 身份校验和提交锁定不变。

依赖：迭代 2 的统一排版/定位结果。宽屏详情区先选一个常用详情面板验证，再扩展。

## 迭代 4：导航一致性与细节打磨（P1）

**当前状态：呈现已统一，焦点恢复未系统验证。** 各面板复用主题、`theme::hints` 提示行和“标签 / 值 / 元数据”三级层次；空会话给出常用入口。浮层关闭后恢复光标、选中项和阅读位置这一项只有既有测试覆盖，没有新增逐面板验证。低频运行指示（动效）没有做。

**用户可见结果：** 面板切换、关闭和状态反馈一致，较少需要记忆快捷键。

工作项：

1. 完善已有 Ctrl+P 命令面板的分类、说明、选中态和空搜索提示；继续复用现有动作定义。
2. 搜索、时间线、工具详情、请求、Context、工作流和历史面板复用主题，统一标题、当前焦点、滚动提示和关闭提示。
3. 明确浮层焦点和 Esc 返回顺序，关闭后恢复原输入光标、选中项与阅读位置；必要的执行操作继续走现有确认流程。
4. 空会话、无结果、无 Agent、断线、历史只读等状态给出具体且简短的下一步提示。
5. 若现有刷新机制足够，增加低频运行指示；动效仅辅助已有状态，未知/断线仍明确标注。刷新成本不合理时直接省略。

验收：只用键盘可完成提交任务、切换 Agent、查看工具、搜索定位、处理请求和返回对话；秘密回答在截图和普通消息预览中持续遮蔽；窗口退出后终端正确恢复。

## 交付顺序与验证

每轮单独验收，优先完成迭代 1，再根据实际截图调整后续方案。建议形成四个可独立评审的里程碑；不在同一个提交中完成所有视觉和交互改造。工期在第一轮完成后根据排版和输入兼容性的实际成本再估算。

每轮交付包含：变更说明、固定场景终端截图、必要的行为回归结果、已知限制。首轮展示完成后即可判断视觉方向，无需等待全部功能完成。

测试优先覆盖真实行为风险：布局裁切、搜索定位、Unicode 光标、缩放后的视图状态、请求身份和提交锁定。复用 Ratatui `TestBackend` 与现有 UI fixture；纯颜色常量无需逐项断言。实际实现后执行仓库基线：

```text
cargo fmt --all -- --check
cargo check --locked --all-targets
cargo clippy --locked --all-targets
cargo nextest run --locked
cargo build --locked --release
```

nextest 不可用时运行 `cargo test --locked --all-targets`。相关终端输入和布局变更还需运行对应 fixture，截图在 Windows Terminal 中核对。截图使用固定脱敏数据。

主题编辑器、插件市场、完整语法高亮、鼠标拖动分栏和复杂动效排在以上四轮之后，待实际使用反馈再确定需求。

## 当前实现与已知限制（2026-10-10）

已修复的回归（均有 `TestBackend` 回归测试）：

- 证据（F11）、工作流（F4）和 Context 面板绘制前先清空区域，底层对话和头部的字符不再从短行后面透出来。这个问题在重做之前就存在。

- 工具摘要行不再重复 `▸` 标记；缩进先从换行宽度中扣除，内容不会被右边界裁掉。
- 搜索定位不再依赖第二套换行算法，窄屏、中文、emoji、组合字符下焦点行与显示行一致。
- 请求面板的标题圆点只属于真正的标题行；多行回答时面板不再盖住输入框；滚到底后 PageUp 第一次按下即生效。
- 工具详情的生命周期值有语义色；续行继承所属字段的样式；工具输出不会被当成字段。
- 只有 UserInput 请求把输入框称为 Answer；审批请求保留任务输入提示，并把 `Ctrl+Y`/`Ctrl+N` 放在快捷键行最前。

已知限制：

- 宽屏详情栏只覆盖请求：终端至少 140 列且有选中的待处理请求时，请求详情显示在对话右侧（不滚动，`F2` 打开可滚动的完整面板）。工具详情仍是覆盖式面板，没有进详情栏。
- 工具组只能用 `Ctrl+E` 整体展开/折叠，不能单独展开某一组。对话区没有行级光标，单组展开需要先引入选择模型。
- 工具摘要的颜色来自 Core 写在摘要文本里的状态词；不认识的状态词保持中性样式。`ConversationItem` 没有结构化的工具状态字段。
- Markdown 只做最小子集，见迭代 2。
- 视觉核对只覆盖合成快照（`running`、`approval`、`request-panel`、`failed`、`empty`、`input`、`commands`、`help`、`tools`），未覆盖时间线、搜索、工具详情、历史、Context 面板的真实终端截图；这些面板只有 `TestBackend` 渲染断言。
- `NO_COLOR` 下层级只靠粗体、反显、缩进和文字区分。

界面语言（2026-10-10 追加）：

- 默认界面为中文，`NATIVE_AGENT_TUI_LANG=en` 切回英文；说明见 `native-agent-tui-ui.md` 第 9 节。本文前面“沿用英文默认界面”的说法已不再成立。
- 只翻译界面文案。Core 和服务端生成的提示、错误、工具摘要里的状态词（`done`、`failed` 等）仍是英文。
- 中文界面在真实终端里核对过主屏、请求详情、命令面板、帮助、时间线、搜索（空查询状态）、证据、工作流（空状态）、Context、Skills（空状态）和宽屏详情栏。工具详情、历史面板，以及有数据时的搜索结果、工作流任务、Skills 条目的中文文案只有 `TestBackend` 测试，没有截图核对。
- 证据面板和时间线详情里的 `Some(..)`/`None` 调试格式在中文界面下显示为值本身或“无”；英文界面保留原样（既有测试以它为契约）。枚举值（如 `TurnStarted`、`ModelRequest`、`TaskId(1)`）两种语言下都还是变体名。
- ConPTY 夹具（`timeline_tui_check.py`、`workflow_tui_check.py`）断言英文文案，已在夹具内固定 `NATIVE_AGENT_TUI_LANG=en`。
- Agent 侧栏由完整方框改为顶线加右侧分隔线。
